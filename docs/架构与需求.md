## 1. 核心公式（四个，可切换）

### 1.1 几何定义

每个**测量位点（site）** = 一个邻面（近中 mesial 或远中 distal），
由 **4 个完全独立的点**确定，按从咬合面到根尖的顺序标：

| 角色 | 含义 |
|------|------|
| `cej` | 釉牙骨质界（CEJ） |
| `cej2` | CEJ 下 2mm |
| `ac` | 牙槽嵴顶（AC） |
| `apex` | 根尖 |

> **根尖点不共享**：近中侧与远中侧各标各的根尖。
> 磨牙近中侧应取近中根根尖、远中侧取远中根根尖，
> 强行共享一个根尖会让多根牙的两侧长轴失真。
>
> ⇒ **一颗牙 = 2 个位点 = 8 个点**。第 n 颗牙编号 `P(8n−7) … P(8n)`。

### 1.2 四个公式

四个公式用**同一组点**，差别只有两处 —— 起点选谁、分子怎么量：

|  | 分子取直线距离 | 分子取长轴投影 |
|---|---|---|
| **起点 = CEJ** | ① `direct_v1` | ② `projection_v1`（默认） |
| **起点 = CEJ 下 2mm** | ③ `direct_cej2_v1` | ④ `projection_cej2_v1` |

终点从不变：分子终点是 AC，分母终点是根尖。记起点为 `O`：

```
直线法    R = ‖AC − O‖ / ‖APEX − O‖
投影法    v = APEX − O ；R = (AC − O)·v / ‖v‖²
```

两种修正各自解决一个问题：

- **投影**剔除 AC 偏在牙侧方的横向分量。数学上**直线法恒 ≥ 投影法**，
  差值即倾斜带来的高估（`tests/test_core.py` 用 300 组随机点验证）。
- **起点后移到 CEJ 下 2mm**把生理性骨改建排除在病理性吸收之外，
  会同时缩短分子与分母。

实现上 `_direct` / `_projection` 按起点参数化，四个公式各是一行调用 ——
将来若再要「某某起点」的变体，加一行即可。

> **兼容**：只标了 3 点的旧数据（无 `cej2`），①② 照常可算，
> ③④ 由 `Formula.__call__` 的 needs 检查如实报「缺 P2」。
> 因此「标完了没」是**相对公式**判定的（`Tooth.complete_for(fml)`），
> 不是一刀切的 4 点。

### 1.3 符号约定与边界

- `h > 0`：AC 位于 CEJ 的**根方** → 存在骨吸收（正常情况）
- `h < 0`：AC 位于 CEJ 的**冠方** → 记为「未见吸收」，`R` **如实存负值**，不截断为 0，导出时保留原值并打 `no_loss` 标记（避免统计时人为偏倚）
- `R > 1`：AC 越过根尖，理论上不可能 → 界面**黄色警告**，提示复核点位，但不阻断
- `L < 20 px`：点位过近，判为误标 → **红色警告**并拒绝写入结果

### 1.4 患者级汇总

```
worst_ratio       = max( 所有位点的 R )          ← 全口最重位点
bone_loss_age_ratio = worst_ratio / age
```

## 2. 输出什么（以及刻意不输出什么）

### 2.1 软件输出

| 项 | 说明 |
|----|------|
| 骨吸收比例 | 最重位点的 `R`，同时给出百分数 |
| 骨吸收年龄比 | `R / 年龄` |
| 影像学骨吸收区间 | `R` 落在 2018 分类的哪一段：`<15%` / `15%–33%` / `>33%` |

### 2.2 ⛔ 刻意不输出 Stage / Grade

2018 新分类的 **Stage** 需要缺牙数、探诊深度、根分叉病变、咬合创伤、咀嚼功能等
临床资料；**Grade** 还需要病史与危险因素（吸烟、糖尿病）。仅凭影像给出
I/II/III/IV 或 A/B/C 是不严谨的，软件不做这件事。

区间只说明数值落点，界面上明确标注「这不是 Stage 分期结论」，最终判断由医生完成。

### 2.3 阈值可配置

区间分界写在 `config/grading.json`，界面「设置」可改，改完对已有数据**一键重算**。

```json
{
  "interval": { "I_max": 0.15, "II_max": 0.33 },
  "validation": { "min_root_px": 20.0, "ratio_warn_above": 1.0 }
}
```

## 3. ★ 架构第一原则：坐标是唯一真相

> **JSON 里永远只存原始点坐标，所有比值、分级都是派生量，运行时算出来。**

这条保证了你换公式时的成本：

| 变更类型 | 代价 |
|---------|------|
| 改分级阈值 | 改 config，重算按钮 → **0 分钟** |
| 改公式（换算法/换分母/加权） | 在 `formula.py` 加一个 20 行函数 + 一行装饰器 → **10 分钟**，70 张片子一键重算，**无需重标** |
| 加一个点位（CEJ 下 2mm 就是这么加的） | `models.ROLES` 加角色 + `Site` 加字段 + 写公式 → 半天。标定步骤、P 编号、导出列都从 `ROLES` 自动派生；**旧数据缺新点位时，需要它的公式自动算不出、老公式照常可用** |
| 改点位语义（比如 CEJ 改成釉牙本质界） | 只影响标注，公式不动 → 0 |

### 3.1 公式引擎

```python
# app/core/formula.py —— 四个公式共用两个参数化实现
def _direct(origin, p, cfg):
    L = g.distance(p["apex"], p[origin])
    h = g.distance(p["ac"], p[origin])
    return Metrics(L, h, h / L, _common_warnings(L, h / L, cfg))


def _projection(origin, p, cfg):
    axis = g.sub(p["apex"], p[origin])
    L = g.norm(axis)
    h = g.projection_length(g.sub(p["ac"], p[origin]), axis)
    return Metrics(L, h, h / L, _common_warnings(L, h / L, cfg))


@formula("direct_v1",       label="① …", needs=("cej", "ac", "apex"))
def direct_v1(p, cfg):        return _direct("cej", p, cfg)

@formula("projection_v1",   label="② …", needs=("cej", "ac", "apex"))
def projection_v1(p, cfg):    return _projection("cej", p, cfg)

@formula("direct_cej2_v1",  label="③ …", needs=("cej", "cej2", "ac", "apex"))
def direct_cej2_v1(p, cfg):   return _direct("cej2", p, cfg)

@formula("projection_cej2_v1", label="④ …", needs=("cej", "cej2", "ac", "apex"))
def projection_cej2_v1(p, cfg): return _projection("cej2", p, cfg)
```

`needs` 既用于计算前的缺点检查，也用于判定「这颗牙按当前公式标完了没」，
还决定画布上长轴从哪个点起画 —— 一处声明，三处生效。

界面右下角常驻显示当前公式名；导出的每条记录都带 `formula_id`，保证可追溯。

### 4.3 原图处理策略

- 导入时**默认复制**到 `images/`（原始文件夹保持不动，防止误操作损坏原始数据）
- 可选「引用模式」：只记录绝对路径，不复制（省磁盘，但原图移动会失联）
- 用 sha1 做指纹，重复导入自动去重

### 4.4 归档策略（重要）

你说的「标注完自动跳到已完成文件夹」——**默认用逻辑归档，不物理移动文件**：

- 状态 `pending / in_progress / done / flagged` 记在 `project.json`
- 左侧列表用 Tab 分组：`待标注 (48)` / `已完成 (25)` / `已标记 (2)`
- 标完点「完成」→ 自动从待标注列表消失、跳到下一张、计数实时更新

> 物理移动文件对研究数据是有风险的（中途改主意要回滚很麻烦）。
> 但在「设置」里提供一个开关：勾上后完成时把图片移动到 `images/done/` 子目录。默认关闭。

### 4.5 名册匹配

导入 `roster.csv` / `.xlsx`，列名自动识别（大小写、中英文兼容）：

| 可识别列名 | 映射 |
|-----------|------|
| `文件名` `filename` `file` `图片` | 匹配键（可含/不含扩展名） |
| `病例号` `编号` `id` `patient_id` | 匹配键（备选） |
| `年龄` `age` | age |
| `性别` `sex` `gender` | sex |
| `备注` `note` | note |

匹配报告弹窗：`成功 68 / 未匹配 5 / 名册中多余 2`，未匹配的高亮列出让你手工对。

### 6.2 批量导入

1. 拖拽文件夹 / 多选文件 → 自动去重、按文件名自然排序（`2` 排在 `10` 前面）
2. 生成缩略图，左侧列表按 `1,2,3…` 编号展示
3. 可选：立即导入名册 CSV 匹配年龄

### 6.3 画框选牙 → 分步放大标定（核心）

**打开片子即进入画框选牙模式，嵴顶曲线同时画好** —— 这是你要的节奏：
曲线一显示就很容易判断哪里低，直接框住那几颗牙。

1. 沿绿色曲线找掉得最低的地方，**拖出 2–3 个方框**把可疑牙框住
   > 框由医生画，所以「牙冠 + 牙根 + 根尖必须完整」由医生直接保证，
   > 软件不做任何猜测。这比点击后自动生成 ROI 更可靠，代码也更简单。
   > 拖拽小于 18px 视为误触，不成框；`Esc` 取消正在画的框。
2. 每画完一个框弹出牙位号输入（带几何推断的默认值，直接回车接受，或敲 `16` 回车）
3. 按 `Enter` → 弹出**分步放大对话框**：
   ```
   ┌── 标定 1/3 · 牙位 16 ────────────────┐
   │                                     │
   │        放大后的单牙图像                │
   │        （含完整牙冠 + 牙根 + 根尖）      │
   │                                     │
   │   当前步骤: P3 近中面 · AC 牙槽嵴顶     │
   │   近中: ✓P1 ✓P2 ●P3 ○P4              │
   │   远中: ○P5 ○P6 ○P7 ○P8              │
   │                                     │
   │   实时: 近中 R=0.42  远中 R=—        │
   │                                     │
   │ [跳过此侧] [上一步] [下一颗 ▸] [完成] │
   └─────────────────────────────────────┘
   ```
   - 按解剖顺序（由咬合面向根尖）引导，**一侧 4 个点走完再走另一侧**：
     `近中 P1 CEJ → P2 CEJ下2mm → P3 牙槽嵴顶 → P4 根尖`
     `远中 P5 CEJ → P6 CEJ下2mm → P7 牙槽嵴顶 → P8 根尖`
   - 步骤表由 `models.ROLES × SURFACES` 自动派生 —— 将来再加点位不用改界面代码
   - **上颌向上、下颌向下**的方向提示随牙位号自动切换
   - 任一点可拖拽微调，实时重算比值
   - 「跳过此侧」：某侧被邻牙遮挡看不清时跳过，该侧不参与取大（编号留空不复用）
   - 放大图上叠加长轴虚线 + AC 到长轴的垂足，**投影关系肉眼可见**；
     长轴起点跟着当前公式走（①②从 CEJ 起、③④从 CEJ 下 2mm 起），所见即所算

4. 全部标完点「完成」→ **自动退出画框模式，回到全景大图看回显**，然后 `Ctrl+Enter` 进入下一张

> **放大画布里装的是完整片子**，只是视野缩放到框上（带 12% 留白）。
> 所以根尖永远不会被裁掉 —— 需要时随手滚轮缩小就能看到整颗牙，
> 而且点坐标天然就是原图坐标，不需要任何 ROI ↔ 原图换算，少一整类 bug。

### 6.4 视觉回显

- 所有点自动映射回全景片原始坐标并绘制
- **不同牙齿不同颜色**（内置 8 色高对比色板，色盲友好）
- **标签命名**：**第 n 颗牙 = `P(8n−7) … P(8n)`**
  | 牙序 | 近中 CEJ/2mm/AC/根尖 | 远中 CEJ/2mm/AC/根尖 |

## 7. 牙槽嵴顶曲线 —— ⛔ 已停用

第二版把曲线从"裸梯度找最强边缘"改成了「区域限制 + 骨/空气剖面判据」，
在真实全景片上确实拉回了牙槽区（实测搜索区 y 0.402–0.678，上颌曲线 0.407–0.499、
下颌 0.573–0.648，均落在解剖预期内）。但个别片子仍会沿牙冠走，
作为"帮医生定位可疑牙位"的辅助不够可靠 —— **宁可不给，也不误导**。

因此界面入口、图层开关、搜索区设置已全部摘除。代码保留在
`app/imaging/bonecrest.py`，连同三条踩坑结论：

1. 不能只看梯度 —— 上颌窦底、眶下缘、下颌管、下颌下缘的边缘都比牙槽嵴强。
2. 定位牙列**不能用 CLAHE 图** —— 它会把上颌窦下缘的骨提亮到超过牙釉质。
3. 也**不能靠"最亮=牙齿"** —— 真实机器输出里下颌骨皮质、颧弓、颈椎和牙釉质一样亮。
   最稳的锚点是**咬合暗带**（几乎恒在纵向 45%–72%）。

将来若接入带 FDI 的分割权重，把牙逐颗抠出来、只在每颗牙的邻面局部找骨缘，
这些结论仍然适用。

## 8. 分割模块的可插拔设计（为将来接 YOLOv8 留口）

```python
# app/imaging/segmenter.py
class ToothSegmenter(ABC):
    @abstractmethod
    def segment(self, img: np.ndarray) -> list[ToothInstance]: ...
    # ToothInstance: fdi | None, mask, bbox, score


class ManualSegmenter(ToothSegmenter):
    """首版：不做实例分割。用户点击 → 基于嵴顶曲线与牙间暗缝
       自适应生成一个必然包含完整牙冠+牙根+根尖的 ROI。"""


class OnnxYoloSegmenter(ToothSegmenter):
    """预留：models/ 下放入 *.onnx 即自动启用，
       界面出现「自动分割」按钮。无权重时该按钮灰显并提示。"""
```

### 8.1 牙位号（FDI）从哪来 —— 不依赖"带 FDI 的权重"

调研结论：**公开的全景片分割权重绝大多数只有单类 `tooth`，不带 FDI 牙位号**
（唯一带 32 类 FDI 的权重是 2.5 GB 的 DINO-SwinL，桌面端装不下）。
因此牙位号采用**几何规则推断 + 人工可改**，不把它绑在模型上：

```
1. 由嵴顶曲线拟合上下颌牙弓 → 判上颌 / 下颌
2. 由全部牙实例重心的 x 中位数定中线 → 判左 / 右
   ⇒ 得到象限号 1 / 2 / 3 / 4
3. 象限内按沿牙弓到中线的弧长排序 ⇒ 得到 1…8
4. 界面上牙位号是一个下拉框 + 「←/→ 移位」按钮，3 秒可改
```

牙列完整时正确率接近 100%，只在缺牙 / 阻生 / 多生牙时偏移一位 —— 而这本就是**标注工具**，
人工修正是产品特性不是缺陷。首版（手动选牙）更简单：**你直接键盘敲 `16` 回车**即可。

ROI 来源（首版）：**医生手动拖框**。不做自动生成 —— 医生画的框天然保证
「牙冠 + 牙根 + 根尖完整」，比任何启发式规则都可靠，且省掉一整套调参。
`ManualSegmenter.roi_at()` 保留为将来自动模式的备用实现，当前不走这条路。

| 组件 | 打包后体积 |
|------|-----------|
| Python 运行时 | ~12 MB |
| PySide6-Essentials（QtCore/Gui/Widgets，剔除 Addons/WebEngine/Quick） | ~55 MB |
| opencv-python-**headless** | ~45 MB |
| numpy | ~25 MB |
| onnxruntime (CPU) | ~16 MB |
| openpyxl（读写 Excel 名册；CSV 用标准库） | ~5 MB |
| 应用代码 + 资源 | ~2 MB |
| **合计（PyInstaller onedir）** | **实测 176.0 MB** ✅（未做剔除时为 268.9 MB） |

### 10.1 三条硬性约束（都是实测踩过的坑）

1. **必须用独立 venv 构建，不能用你现在的全局环境。**
   本机全局环境同时装了 `opencv-python 4.13` 与 `opencv-python-headless 5.0` ——
   `opencv-python` 自带一套 Qt，**PyInstaller 禁止一个冻结应用里出现两套 Qt binding，会直接 abort 构建**。
2. **只装 `PySide6-Essentials`，绝不装完整 `PySide6`。** 后者会拉进 168 MB 的 Addons（含 QtWebEngine 解压后 ~130 MB）。
3. **显式 exclude**：`PySide6.QtWebEngineWidgets` / `QtWebEngineCore` / `QtQuick` / `QtMultimedia` / `QtUiTools`（它的 hook 会反向拉进 WebEngine 插件）/ `tkinter` / `matplotlib` / `scipy` / `skimage` / `pandas` / `torch`。

### 10.2 其他

- **不引入 pandas**（省 ~35 MB）：CSV 用标准库 `csv`，Excel 用 `openpyxl`，需求量很小。
- 分发形式：**`--onedir` + Inno Setup 安装包**。不用 `--onefile` —— 每次启动都要解压到临时目录，冷启动 1.8s vs 0.08s，对天天用的标注工具是灾难。
- 若将来加 ONNX 权重：必须用 `n` / `s` 尺寸（7–24 MB）。`l` / `x` 尺寸导出 fp32 ONNX 会到 126 / 230 MB，**比整个应用还大**，直接出预算。
